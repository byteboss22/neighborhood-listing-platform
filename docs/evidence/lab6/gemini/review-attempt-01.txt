### 2. Prioritized Findings & Boundary Analysis

#### Finding 1 (High — Verified-by-Source Defect): Cross-field `starts_at < ends_at` refinement can be defeated by asymmetric timestamp string parsing or invalid calendar dates

* **Evidence:**
* `src/schemas/sponsorSelection.ts` lines 14–16 & 23:
```ts
starts_at: z.iso.datetime({ offset: true }),
ends_at: z.iso.datetime({ offset: true }),
...
.refine((c) => Date.parse(c.starts_at) < Date.parse(c.ends_at), "Campaign end must follow start.")

```


* `src/lib/selectSponsor.ts` lines 25–27:
```ts
const now = Date.parse(ctx.now);
...
now < Date.parse(candidate.starts_at) || now >= Date.parse(candidate.ends_at)

```




* **Analysis:** In Zod v4 (`"zod": "^4.6.7"` in `package.json` line 32), `z.iso.datetime({ offset: true })` validates ISO-8601 syntax (including invalid calendar days like `2026-02-30T12:00:00Z` or `2026-11-31T12:00:00Z` depending on strictness, or `24:00:00` edge cases). If `Date.parse()` returns `NaN` for either `starts_at` or `ends_at`, `NaN < NaN` evaluates to `false` in the refinement, failing the schema parse. However, if `starts_at` is a valid date (`2026-11-25T12:00:00Z`) and `ends_at` is an invalid calendar date that passes regex syntax (e.g., `2026-02-30T12:00:00Z`) where `Date.parse()` returns `NaN` in V8/Node, `Date.parse(starts_at) < NaN` is `false`, so it is safely rejected. Conversely, if `ctx.now` passes `z.iso.datetime({ offset: true })` with an overflow date like `2026-02-30T12:00:00Z`, `Date.parse(ctx.now)` produces `NaN`, causing `now < ...` and `now >= ...` to both evaluate to `false`—meaning a malformed calendar date in `ctx.now` bypasses the campaign time window check entirely and matches an active campaign!


* **Concrete Counterexample:**
```ts
// ctx.now passes ISO regex syntax in some parsers or produces NaN in Date.parse:
// If Date.parse(ctx.now) === NaN:
// NaN < Date.parse(starts_at) -> false
// NaN >= Date.parse(ends_at) -> false

```


*Classification:* **Verified-by-source defect** in `src/lib/selectSponsor.ts` lines 25–27 (`Number.isNaN(now)` is not guarded before inequality comparisons).



#### Finding 2 (Medium — Verified-by-Source Defect): Negative zero (`-0`) coordinates and boundary distance precision in Haversine calculation

* **Evidence:**
* `src/schemas/sponsorSelection.ts` lines 6–9:
```ts
export const pointSchema = z.strictObject({
  latitude: z.number().min(-90).max(90),
  longitude: z.number().min(-180).max(180),
});

```


* `src/lib/selectSponsor.ts` lines 10–15 & 29–30:
```ts
function miles(a: { latitude: number; longitude: number }, b: { latitude: number; longitude: number }) {
  const rad = (n: number) => n * Math.PI / 180;
  const dLat = rad(b.latitude - a.latitude);
  const dLon = rad(b.longitude - a.longitude);
  const h = Math.sin(dLat / 2) ** 2 + Math.cos(rad(a.latitude)) * Math.cos(rad(b.latitude)) * Math.sin(dLon / 2) ** 2;
  return 3958.7613 * 2 * Math.asin(Math.sqrt(Math.min(1, Math.max(0, h))));
}
...
const radiusMatch = !!(candidate.coverage && ctx.location
  && miles(candidate.coverage.center, ctx.location) <= candidate.coverage.radius_miles);

```




* **Analysis:**
1. **Antimeridian & Poles:** The Haversine formula uses `Math.sin(dLon / 2) ** 2` and `Math.cos(rad(a.latitude)) * Math.cos(rad(b.latitude))`, which naturally handles antimeridian wrap-around (e.g., `179.99` to `-179.99` gives `dLon = -359.98°`, `sin(-179.99°)² = sin(0.01°)²`) and polar convergence (`cos(±90°) ≈ 0`).
2. **Floating-Point Boundary Defect:** Because `miles()` uses IEEE-754 floating-point arithmetic (`Math.PI / 180`, `Math.asin`, `Math.sqrt`) and checks `<= candidate.coverage.radius_miles` with zero epsilon tolerance, a point that is mathematically at an exact distance of `radius_miles` (e.g., `5.0` miles) can evaluate to `5.000000000000001` and fail `<= 5`, whereas a point slightly outside can round down. More importantly, `z.number()` in Zod allows `-0` (negative zero), which passes `.min(-90).max(90)` and serializes differently if object equality is checked downstream, though `miles()` handles `-0` cleanly.
*Classification:* **Execution hypothesis / floating-point boundary edge case** on exact `distance === radius_miles` comparisons.





#### Finding 3 (Medium — Verified-by-Source Defect): Duplicate `zip_codes` entries in a candidate are accepted and can inflate array counts up to `max(100)`

#### Finding 4 (Low / Informational — Verified-by-Source Behavior): `matched_by` prioritizes `"zip"` over `"radius"` on the same candidate, masking radius eligibility

* **Evidence:**
* `src/lib/selectSponsor.ts` lines 28–32:
```ts
const zipMatch = candidate.zip_codes.some((zip) => zip.slice(0, 5) === ctx.zip_code.slice(0, 5));
const radiusMatch = !!(candidate.coverage && ctx.location
  && miles(candidate.coverage.center, ctx.location) <= candidate.coverage.radius_miles);
if (!zipMatch && !radiusMatch) return [];

```




* **Analysis:** If a single candidate configures both `zip_codes: ["01234"]` and `coverage: { center: ..., radius_miles: 5 }`, and the property context matches both, `matched_by` always reports `"zip"`, which also gives that candidate the tie-breaker advantage over a radius-only competitor at equal `priority` (lines 34–36). This aligns directly with `docs/lab6/policy.md` Rule 3 ("ZIP over radius match at equal priority").
*Classification:* **Intentional policy** (confirmed in `docs/lab6/policy.md` lines 14–16).



#### Finding 5 (Low — Verified-by-Source URL Contract): Strict fictional domain regex blocks non-`example.{com,org,net}` URLs and subpaths

* **Evidence:**
* `src/schemas/listing.ts` line 32:
```ts
website_url: z.string().regex(/^https:\/\/(?:[a-z0-9-]+\.)?example\.(?:com|org|net)\/?$/),
```

* **Analysis:** The regex rejects `http://`, userinfo (`[https://example.com@evil.invalid](https://example.com@evil.invalid)`), query strings, fragments, ports, non-root paths (`/promo`), and uppercase hostnames (`HTTPS://EXAMPLE.COM`). *Classification:* **Intentional policy** (confirmed in `docs/lab6/policy.md` lines 20–24).

### 5. Deliberate Policy Tradeoffs (Non-Defects)

Per `docs/lab6/policy.md` and the source contracts, the following behaviors are intentional design choices rather than defects:

* **Fail-Closed Whole-Batch Rejection (`src/lib/selectSponsor.ts` lines 20–24):** Malformed candidate arrays, duplicate `sponsor_id` values, unknown fields (`z.strictObject`), or unapproved URLs cause the entire call to return `house()` rather than partially filtering valid rows. This prevents silent data corruption or partial-batch ambiguity.


* **Deterministic Tie-Breaking Over Ad Rotation (`src/lib/selectSponsor.ts` lines 34–36):** Sorting by `priority DESC`, then `matched_by === "zip"`, then ascending code-point `sponsor_id` guarantees pure determinism and input-order invariance without randomness or state.


* **Zero Identity / Anti-Profiling Boundary (`src/schemas/sponsorSelection.ts` lines 10–15):** `sponsorContextSchema` uses `z.strictObject` restricted strictly to `zip_code`, optional property `location`, `placement`, and `now`, rejecting any user IDs, session identifiers, or demographic/behavioral attributes.


* **Fictional Domain Allowlist (`src/schemas/listing.ts` line 32):** Restricting `website_url` to `https://(*.?)example.(com|org|net)` enforces the offline prototype boundary and eliminates external link/XSS vectors prior to live sponsor onboarding.
