This is a static review of the code. I did not run any tests or builds, and I did not connect to your database.

## Confirmed behaviors that likely go against the assignment's intent

These are definite readings of the code. Whether each one counts as a defect depends on what the assignment means by "suspended" and "modify".

### 1. Providers can lift their own suspension
**Code:** [migration:68](supabase/migrations/20261029140000_exam_services_persistence.sql#L68) grants UPDATE on `status`, and the update policy at [94-100](supabase/migrations/20261029140000_exam_services_persistence.sql#L94-L100) allows `status IN ('draft','suspended')` on both the old row and the new row.

**Impact:** A provider can run `UPDATE services SET status='draft' WHERE id=<suspended>` and undo an admin suspension. They can also mark their own drafts as suspended. They still can't reach `pending` or `approved`, but if suspension is a moderation tool it no longer holds. [security.test.ts:75-91](tests/security.test.ts#L75-L91) only tests changing the title, never moving between draft and suspended.

**Fix:** Remove `status` from the column grant on line 68 so providers can edit content but not status. Status changes stay with `service_role`.
- **Positive test:** the provider updates `title` on their suspended service and gets 1 row back.
- **Negative test:** the provider runs `SET status='draft'` on a suspended service. It is rejected with `permission denied`, and the row is still `suspended` when read through `service_role`.

### 2. Deleting a suspended service also deletes its bookings
**Code:** the delete policy at [102-105](supabase/migrations/20261029140000_exam_services_persistence.sql#L102-L105) together with `ON DELETE CASCADE` on `bookings.service_id` at [line 38](supabase/migrations/20261029140000_exam_services_persistence.sql#L38). [security.test.ts:90](tests/security.test.ts#L90) asserts that this delete succeeds.

**Impact:** A suspended provider can wipe out client booking records and evidence that moderators might need.

**Fix:** Limit DELETE to `status = 'draft'`, or change the bookings foreign key to `ON DELETE RESTRICT`.
- **Positive test:** the provider deletes a draft service with no bookings and gets 1 row back.
- **Negative test:** the provider deletes a suspended service that has a booking. They get 0 rows or an error, and the booking count seen through `service_role` doesn't change.

### 3. Bookings are accepted for services that aren't approved
**Code:** `WITH CHECK (true)` at [112-113](supabase/migrations/20261029140000_exam_services_persistence.sql#L112-L113). Foreign-key checks ignore RLS, so a draft, pending or suspended service UUID is accepted. [bookings/route.ts:16](src/app/api/bookings/route.ts#L16) returns 400 for a UUID that doesn't exist and 201 for one that does. That lets a caller test whether a hidden service exists.

**Impact:** Low in practice, because UUIDv4 values can't realistically be guessed. Still, it is a side channel around "anonymous sees approved only", and it lets people book services that aren't live. Your comment on line 110 says the open insert is deliberate. If the exam text really says "any service", keep it and document it.

**Fix:** `WITH CHECK (EXISTS (SELECT 1 FROM public.services s WHERE s.id = service_id AND s.status = 'approved'))`. This works for `anon` because `id` and `status` are in its column grant. Map the resulting `42501` error to the same 400 that a missing service gets.
- **Positive test:** booking an approved service returns 201.
- **Negative test:** booking a draft service's UUID is rejected, and the API response is byte-for-byte identical to the one for a random UUID.

### 4. Category links are visible even when the category is inactive
**Code:** [107-108](supabase/migrations/20261029140000_exam_services_persistence.sql#L107-L108) only checks that the service is approved.

**Impact:** Anonymous users can see the UUIDs of inactive categories that are linked to approved services, though not their names. It's minor, but it doesn't fully match "active categories only".

**Fix:** Add `AND EXISTS (SELECT 1 FROM public.service_categories c WHERE c.id = category_id AND c.active_status)`.
- **Positive test:** a link from an approved service to an active category is visible to `anon`.
- **Negative test:** after deactivating that category, `anon` gets 0 links.

### Hardening (not defects)
- **Bookings SELECT for `anon`:** [Line 71](supabase/migrations/20261029140000_exam_services_persistence.sql#L71) grants it, but no policy targets `anon`, so it returns 0 rows. Revoking it means a policy added by mistake later couldn't expose client emails.
- **`provider_id` readable by any signed-in user:** [Line 64](supabase/migrations/20261029140000_exam_services_persistence.sql#L64) gives full SELECT on approved services to every authenticated user. A signed-in client calling Supabase directly can read `provider_id`. Your API doesn't expose it.
- **Input limits:** `title` and `notes` have no maximum length, a title of five spaces passes validation, `requested_date` accepts past dates, and public booking inserts have no rate limit. None of these are in your requirements.

## Hypotheses (can't be checked from code)
1. **Your hosted database may not match the migration.** Policies or grants added in the Supabase dashboard would change every conclusion above. [exam_rls_catalog.sql](supabase/tests/exam_rls_catalog.sql) only counts policies per table, so a weakened policy would still pass.
   - **Check:** query `pg_policies` (`qual`, `with_check`), `information_schema.role_table_grants` and `column_privileges`.
   - **Positive:** the output matches the migration exactly.
   - **Negative:** an added `USING (true)` policy causes a mismatch.
2. **Your local RLS test setup may behave differently from hosted Supabase.** [security.test.ts:22](tests/security.test.ts#L22) builds its own roles and `auth.uid()`, so differences in JWT claims or default privileges wouldn't show up there.
3. **`/api/services` could become a static 503.** If a build ever runs without `SUPABASE_URL` set, `required()` throws before any network call, and the handler might be prerendered as that error. Your recorded build doesn't show this. Check the route table on each deployed build.
