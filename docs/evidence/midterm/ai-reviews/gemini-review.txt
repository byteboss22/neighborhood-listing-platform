### Requirement 3: Anonymous Users See Approved Services & Active Categories Only

* **Files Reviewed**: [20261029140000_exam_services_persistence.sql](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/supabase/migrations/20261029140000_exam_services_persistence.sql#L61-L83).
* **Implementation Analysis**:
  * **Categories**:
    ```sql
    CREATE POLICY categories_active_read ON public.service_categories
      FOR SELECT TO anon, authenticated
      USING (active_status = true);
    ```
    Anonymous callers only match rows where `active_status` is `true`. Inactive categories return 0 rows.
  * **Services**:
    ```sql
    GRANT SELECT (id, title, hourly_rate, duration_minutes, coverage_radius_miles, status, created_at)
      ON public.services TO anon;
    CREATE POLICY services_public_read ON public.services
      FOR SELECT TO anon, authenticated
      USING (status = 'approved');
    ```

    The RLS policy restricts visibility exclusively to `status = 'approved'`. Draft, pending, and suspended records evaluate to false. Furthermore, the column grant explicitly omits `provider_id`, ensuring anonymous callers cannot query provider identities at the SQL level.
  * **Mappings**:
    ```sql
    CREATE POLICY mappings_approved_read ON public.service_category_mappings
      FOR SELECT TO anon, authenticated
      USING (EXISTS (SELECT 1 FROM public.services s WHERE s.id = service_id AND s.status = 'approved'));
    ```
* **Finding**: **Compliant / No Defect**. RLS policies and column-level privileges ensure anonymous actors cannot observe inactive categories or unapproved services.

### Requirement 4: Merchants/Providers Can Modify Only Their Own Draft or Suspended Services

* **Files Reviewed**: [20261029140000_exam_services_persistence.sql](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/supabase/migrations/20261029140000_exam_services_persistence.sql#L68-L105).
* **Implementation Analysis**:
  * **Update Guardrails**:
    ```sql
    CREATE POLICY services_provider_update ON public.services
      FOR UPDATE TO authenticated
      USING (provider_id = (SELECT auth.uid()) AND status IN ('draft', 'suspended') AND EXISTS (
        SELECT 1 FROM public.profiles p WHERE p.id = (SELECT auth.uid()) AND p.role IN ('merchant', 'provider')
      ))
      WITH CHECK (provider_id = (SELECT auth.uid()) AND status IN ('draft', 'suspended') AND EXISTS (
        SELECT 1 FROM public.profiles p WHERE p.id = (SELECT auth.uid()) AND p.role IN ('merchant', 'provider')
      ));
    ```
    * `USING` verifies that the existing record belongs to `auth.uid()` and is currently in `draft` or `suspended` status. Any attempt to update an `approved` or `pending` service, or a service owned by another provider, fails to match (yielding 0 affected rows).
    * `WITH CHECK` verifies that the updated row remains in `draft` or `suspended` status and remains owned by `auth.uid()`, preventing self-approval or privilege escalation.
    * Line 68 omits `provider_id` from `GRANT UPDATE (...)`, making ownership transfer impossible at the PostgreSQL grant level.
  * **Delete Guardrails**:
    ```sql
    CREATE POLICY services_provider_delete ON public.services
      FOR DELETE TO authenticated
      USING (provider_id = (SELECT auth.uid()) AND status IN ('draft', 'suspended') AND EXISTS (
        SELECT 1 FROM public.profiles p WHERE p.id = (SELECT auth.uid()) AND p.role IN ('merchant', 'provider')
      ));
    ```
* **Finding**: **Compliant / No Defect**. Both `USING` and `WITH CHECK` clauses enforce that providers cannot modify or delete services outside their own `draft` or `suspended` listings.

### Requirement 5: Public Visitors May Insert Bookings; Clients Cannot Read Bookings

* **Files Reviewed**: [20261029140000_exam_services_persistence.sql](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/supabase/migrations/20261029140000_exam_services_persistence.sql#L70-L71), [route.ts](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/src/app/api/bookings/route.ts#L12-L18).
* **Implementation Analysis**:
  * **Public Insertion**:
    ```sql
    GRANT INSERT (service_id, client_email, requested_date, notes) ON public.bookings TO anon, authenticated;
    CREATE POLICY bookings_public_insert ON public.bookings FOR INSERT TO anon, authenticated WITH CHECK (true);
    ```
    Visitors (both `anon` and `authenticated`) can insert bookings.
  * **Zero Read Access for Clients**:
    * In PostgreSQL: No SELECT policy is created for `anon` on `bookings` (default deny). For `authenticated`, the only SELECT policy is `bookings_provider_read`, which checks `p.role IN ('merchant', 'provider')` and `s.provider_id = auth.uid()`. Because a client has `p.role = 'client'`, the check evaluates to `false`. Clients see 0 rows.
    * In the API: [src/app/api/bookings/route.ts](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/src/app/api/bookings/route.ts#L15-L18) does not expose a `GET` handler, invokes `insert()` without `.select()`, and returns `{ received: true }, 201`, preventing any echo or leakage of client contact details.
* **Finding**: **Compliant / No Defect**. Clients cannot read booking records through either PostgREST or the Next.js API layer.

### Requirement 6: Providers Can Read Bookings Only for Their Own Services

* **Files Reviewed**: [20261029140000_exam_services_persistence.sql](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/supabase/migrations/20261029140000_exam_services_persistence.sql#L115-L119).
* **Implementation Analysis**:
  ```sql
  CREATE POLICY bookings_provider_read ON public.bookings FOR SELECT TO authenticated
    USING (EXISTS (
      SELECT 1 FROM public.services s JOIN public.profiles p ON p.id = s.provider_id
      WHERE s.id = service_id AND s.provider_id = (SELECT auth.uid()) AND p.role IN ('merchant', 'provider')
    ));
  ```
  * When a provider queries `public.bookings`, the subquery joins `services` and `profiles`.
  * Only bookings whose foreign key matches a service owned by the caller (`s.provider_id = auth.uid()`) where the caller's verified role is `merchant` or `provider` are returned.
  * Bookings for services owned by other providers return 0 rows.
* **Finding**: **Compliant / No Defect**. Booking visibility is strictly bound to service ownership and provider role verification.

### Detailed Findings

#### Finding HYP-01: Booking Insert Policy Allows Targeting Draft or Suspended Services

* **Classification**: **Hypothesis / Assignment Discrepancy** (Complies with literal assignment instructions, but constitutes a data integrity risk in production).
* **File & Code Reference**:
  * [20261029140000_exam_services_persistence.sql:112-113](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/supabase/migrations/20261029140000_exam_services_persistence.sql#L112-L113)
    ```sql
    CREATE POLICY bookings_public_insert ON public.bookings FOR INSERT TO anon, authenticated
      WITH CHECK (true);
    ```
  * [src/app/api/bookings/route.ts:15-16](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/src/app/api/bookings/route.ts#L15-L16)
* **Impact**:
  * The foreign key constraint ensures that `service_id` exists in `public.services`. However, `WITH CHECK (true)` does not verify that the referenced service is `approved`.
  * If an attacker discovers or guesses the UUID of a service that is currently in `draft`, `pending`, or `suspended` status, they can successfully insert bookings against it.
  * *Note*: The code comments and `docs/requirements.md` note that this was implemented deliberately based on the prompt *"public and authenticated callers can insert for any existing service"*. For production, this should restrict insertion to approved services.
* **Verification Tests**:
  * **Positive Test**: Submit a booking payload with a valid `service_id` belonging to an `approved` service $\rightarrow$ Request succeeds with HTTP 201 (`{ received: true }`).
  * **Negative Test**: Submit a booking payload referencing a known `draft` or `suspended` `service_id` $\rightarrow$ Currently succeeds (returns 201); under hardened logic (`WITH CHECK (EXISTS (SELECT 1 FROM public.services s WHERE s.id = service_id AND s.status = 'approved'))`), the database should reject the insert with RLS error `42501`.

#### Finding HYP-02: Unbounded String Lengths for `title` and `notes`

* **Classification**: **Hypothesis / Security Hardening** (Resource Exhaustion / DoS).
* **File & Code Reference**:
  * [src/schemas/service.ts:4-6](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/src/schemas/service.ts#L4-L6)
    ```typescript
    const title = z.string().refine((value) => [...value].length >= 5, {
      message: "Title must contain at least 5 characters.",
    });
    ```
  * [src/schemas/booking.ts:7-9](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/src/schemas/booking.ts#L7-L9)
    ```typescript
    notes: z.string().refine((value) => [...value].length >= 10, {
      message: "Notes must contain at least 10 characters.",
    })
    ```
* **Impact**:
  * While minimum lengths (`>= 5` for title, `>= 10` for notes) and numeric boundaries (`hourly_rate <= 99999999.99`, integer max `2147483647`) are strictly bounded, string fields do not specify an upper bound (e.g., `.max(200)`).
  * In PostgreSQL, `title TEXT` and `notes TEXT` can store up to 1 GB.
  * A caller could submit exceptionally large strings (e.g., megabytes of text in `notes` or `title`), causing database storage inflation, memory pressure in query deserialization, or layout degradation in client UI components.
* **Verification Tests**:
  * **Positive Test**: Submit a payload with `title` of 60 characters and `notes` of 200 characters $\rightarrow$ Validates successfully and creates record.
  * **Negative Test**: Submit a payload with a `title` containing 5,000 characters $\rightarrow$ Currently passes schema validation; when hardened with `title.max(150)`, schema validation should reject the payload with HTTP 400 and an issue on path `["title"]`.

#### Finding HYP-04: Unqualified Column Reference in `bookings_provider_read` Policy

* **Classification**: **Hypothesis / Schema Maintainability**.
* **File & Code Reference**:
  * [20261029140000_exam_services_persistence.sql:115-119](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/supabase/migrations/20261029140000_exam_services_persistence.sql#L115-L119)
    ```sql
    CREATE POLICY bookings_provider_read ON public.bookings FOR SELECT TO authenticated
      USING (EXISTS (
        SELECT 1 FROM public.services s JOIN public.profiles p ON p.id = s.provider_id
        WHERE s.id = service_id AND s.provider_id = (SELECT auth.uid()) AND p.role IN ('merchant', 'provider')
      ));
    ```
* **Impact**:
  * In the subquery `WHERE s.id = service_id`, `service_id` is unqualified. Because `public.services` only has `id` (and no `service_id` column), PostgreSQL resolves `service_id` to `public.bookings.service_id` from the outer query.
  * While this functions correctly under the current schema, if a future migration were to add a column named `service_id` to `public.services`, PostgreSQL's scope resolution would shadow the outer column, breaking the policy.
* **Verification Tests**:
  * **Positive Test**: Execute `SELECT * FROM public.bookings` as an authenticated provider who owns service `S1` $\rightarrow$ Successfully returns bookings matching `bookings.service_id = S1`.
  * **Negative Test / Defense**: Replace `s.id = service_id` with `s.id = public.bookings.service_id` $\rightarrow$ The query remains explicit and immune to future column additions on `public.services`.

#### Finding HYP-05: Public Booking Endpoint Lacks Rate Limiting

* **Classification**: **Hypothesis / Operational Security**.
* **File & Code Reference**:
  * [src/app/api/bookings/route.ts:5-22](file:///Users/ejuarez/Documents/Github/neighborhood-listing-platform-main/src/app/api/bookings/route.ts#L5-L22)
* **Impact**:
  * The `POST /api/bookings` route is publicly exposed to accept anonymous appointment requests.
  * Without an edge rate-limiter (e.g., Upstash / Redis token bucket or IP-based rate limiting), an automated script could flood the `bookings` table with high volumes of synthetic requests, causing denial of service or filling database storage.
* **Verification Tests**:
  * **Positive Test**: Send a single legitimate booking request $\rightarrow$ Returns 201 Created.
  * **Negative Test**: Send 50 sequential booking requests within 1 second from a single client $\rightarrow$ Currently all 50 succeed; with rate limiting enabled, subsequent requests should receive HTTP 429 Too Many Requests.
